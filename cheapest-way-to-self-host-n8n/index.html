How much RAM does n8n actually need?

This is the question that decides your bill, and most guides answer it badly.

n8n's own docs suggest a minimum of 512MB. That number is technically true and practically useless. It describes n8n sitting idle doing nothing.

Here is what actually happens:

RAMWhat worksWhat breaks
1GBn8n starts, simple webhooks runDies on any workflow handling a large HTTP response or file
2GBLight workflows, a few nodesStruggles once you add Postgres in the same box
4GBMost real setups: n8n + Postgres + a couple of other containersHeavy data transforms, big batches
8GBComfortable, room for other services—

The reason is that n8n holds workflow execution data in memory. A workflow that fetches a 50MB JSON response and runs it through a few transform nodes can spike well past what the container idles at. When it exceeds available memory, the Node process is killed and your execution just... vanishes.

Practical recommendation: start at 4GB. If you are running Postgres in the same box (you should — more on that below) and want headroom, 8GB.

The database decision that costs people their data

n8n defaults to SQLite. It works. It is also the single most common cause of "I lost all my workflow history" posts.

SQLite is a single file. Under concurrent writes — which is exactly what happens when several workflows fire at once — it can corrupt. It also does not handle n8n's execution-pruning well once you have tens of thousands of rows.

Use PostgreSQL. It is one extra container in your Compose file:

services:
  postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n"]
      interval: 10s
      timeout: 5s
      retries: 5

  n8n:
    image: docker.n8n.io/n8nio/n8n
    restart: unless-stopped
    ports:
      - "127.0.0.1:5678:5678"
    environment:
      - DB_TYPE=postgresdb
      - DB_POSTGRESDB_HOST=postgres
      - DB_POSTGRESDB_DATABASE=n8n
      - DB_POSTGRESDB_USER=n8n
      - DB_POSTGRESDB_PASSWORD=${POSTGRES_PASSWORD}
      - N8N_HOST=${DOMAIN}
      - N8N_PROTOCOL=https
      - WEBHOOK_URL=https://${DOMAIN}/
      - GENERIC_TIMEZONE=Asia/Kolkata
      - N8N_ENCRYPTION_KEY=${N8N_ENCRYPTION_KEY}
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

volumes:
  postgres_data:
  n8n_data:

Two things in there that matter more than they look:

ports: "127.0.0.1:5678:5678" binds n8n to localhost only. Without the 127.0.0.1: prefix, Docker publishes the port to the world and bypasses UFW entirely — your n8n instance is on the public internet with no auth in front of it. This catches a lot of people.

N8N_ENCRYPTION_KEY encrypts your stored credentials. If you do not set it, n8n generates one and stores it in the data volume. Lose the volume, lose every saved credential. Set it explicitly and keep it in your password manager.

Setup

1. Get a VPS

Pick a plan with at least 4GB RAM. Location matters for webhook latency — choose a region near you or near the services you integrate with.

2. Point a domain at it

You need HTTPS for webhooks. Most third-party services refuse to send webhooks to plain HTTP, and some refuse self-signed certificates too.

Add an A record for n8n.yourdomain.com pointing at the VPS IP.

3. Install Docker

curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
newgrp docker

4. Reverse proxy + TLS

Caddy is the shortest path — it handles certificates automatically:

sudo apt install -y caddy

/etc/caddy/Caddyfile:

n8n.yourdomain.com {
    reverse_proxy 127.0.0.1:5678
}
sudo systemctl reload caddy

That is the whole TLS setup. Caddy requests the certificate on first request and renews it automatically.

5. Firewall

sudo ufw allow OpenSSH
sudo ufw allow 80,443/tcp
sudo ufw enable

Note there is no rule for 5678 — it should not be reachable from outside. If you skipped the 127.0.0.1: bind above, add sudo ufw deny 5678/tcp as well, but fixing the bind is the correct solution.

6. Start it

docker compose up -d
docker compose logs -f n8n

The backup nobody sets up until it is too late

Self-hosting means backups are your problem. A single cron job covers it:

#!/bin/bash
# /root/backup-n8n.sh
set -euo pipefail
BACKUP_DIR=/root/n8n-backups
mkdir -p "$BACKUP_DIR"
STAMP=$(date +%Y%m%d)

docker compose -f /root/n8n/docker-compose.yml exec -T postgres \
  pg_dump -U n8n n8n | gzip > "$BACKUP_DIR/n8n-$STAMP.sql.gz"

# keep 14 days
find "$BACKUP_DIR" -name 'n8n-*.sql.gz' -mtime +14 -delete
chmod +x /root/backup-n8n.sh
(crontab -l 2>/dev/null; echo "0 3 * * * /root/backup-n8n.sh") | crontab -

Then copy those off the server. A backup that lives only on the machine it is backing up is not a backup.

What about the free options?

Oracle Cloud Always Free gives you an ARM instance with 24GB RAM. It is a genuinely remarkable free tier and n8n runs fine on ARM. The catch: account approval is inconsistent, and Oracle has been known to reclaim idle free-tier instances. Fine for experimenting, risky for anything you depend on.

Raspberry Pi at home. Works. But now your automation uptime is tied to your home internet, your power supply, and your dynamic IP. You will spend more time maintaining it than the $7/month you saved is worth.

Free-tier PaaS (Render, Railway, Fly.io). These sleep on inactivity, which breaks scheduled workflows and delays webhooks. Their paid tiers cost more than a VPS.

The honest summary: free options are good for learning n8n. They are a bad idea for automations that other things depend on.

When self-hosting is the wrong choice

I would rather you not waste a weekend, so:

  • You run 1-3 simple workflows. n8n Cloud's free tier or Starter is fine.

The time you spend on server maintenance is worth more than $24.

  • You do not want to think about Linux. Updates, TLS renewal, disk space,

backups — it is not much work, but it is never zero.

  • You need enterprise SSO, SOC2, or an SLA. That is what n8n Cloud sells.

Self-hosting makes sense at roughly 5+ active workflows, or when your data genuinely cannot leave your infrastructure, or when you want to run other services on the same box anyway. That last one is the real argument: a VPS running n8n has plenty of spare capacity for whatever else you need.

FAQ

How much does self-hosted n8n cost per month?

Around $7-13/month for a VPS with 4-8GB RAM, which is enough for most setups. The n8n software itself is free under the Sustainable Use License. Your only other likely cost is a domain, roughly $10-15/year.

Is self-hosting n8n free?

The software is free, the hosting is not. You can get to genuinely $0 using Oracle Cloud's free tier or a Raspberry Pi you already own, but both trade reliability for cost. Realistically, budget $7-13/month.

How much RAM does n8n need?

4GB is the practical minimum for a real setup running n8n plus PostgreSQL. n8n's docs mention 512MB, but that only covers an idle instance. Workflows that handle large payloads will exceed it and get killed by the OOM killer.

Should I use SQLite or PostgreSQL for n8n?

PostgreSQL. SQLite is the default and works for light use, but it is prone to corruption under concurrent workflow executions and handles large execution tables poorly. Postgres is one extra container and removes an entire category of problem.

Can I run n8n without Docker?

Yes, via npm (npm install n8n -g), but you then manage Node versions, process supervision, and dependency conflicts yourself. Docker is less work and makes upgrades a single command.

Is self-hosted n8n slower than n8n Cloud?

No, usually the opposite — a dedicated VPS is not shared with other tenants. What you lose is n8n Cloud's managed scaling and their handling of very high webhook concurrency, which most self-hosted users never approach.
